## 1. 문제 정의

> 흩어진 학사 정보와 질의응답 게시판의 복잡한 접근 경로로 학생들이 원하는 정보를 찾기 어렵고,
> 관리자는 같은 문의를 반복 응대하고 있다.

### 1.1 두 사용자의 문제

| 학생 | 관리자 |
| --- | --- |
| 흩어진 공지와 복잡한 홈페이지 구조 때문에 원하는 정보를 찾기 어렵다 | 질의응답 게시판에 답변을 써도 **비밀글이 많아** 같은 질문이 반복된다 |
| 질의응답 게시판의 존재나 위치를 잘 모른다 | 전화 문의가 많아 동일한 내용을 반복해서 안내해야 한다 |

### 1.2 기존 방식의 불편

- 홈페이지 내 질의응답 게시판의 접근 경로가 복잡하다.
- 게시판의 존재 자체를 모르는 학생도 많다.
- 결국 **전화 문의가 가장 많이 사용**된다.
- 동일한 질문이 반복되어 담당자의 업무가 증가한다.

### 1.3 목표

- **학생** — 원하는 정보를 빠르게 찾을 수 있게 한다.
- **관리자** — 반복 문의를 줄여 업무 부담을 감소시킨다.

---

## 2. 핵심 사용자와 사용 상황

- **사용자**: 강남대학교 재학생 — 전부전과, 수강신청, 휴학 등 학사 행정 정보를 찾는 학생.
- **사용 상황**: 전부전과·수강신청·휴학 등 **시즌별 학사 일정이 다가왔을 때**, 관련 정보를 빠르게 확인하거나 문의하기 위해 문무니를 이용한다.

시즌성이 강한 서비스이므로, 홈 화면의 카테고리·인기 검색어처럼 **그 시기에 많이 찾는 주제를 앞에 노출**하는 구성이 중요합니다.

---

## 3. 해결 방식

문무니는 **문의 중심 학사 안내 웹서비스**입니다. 학생이 질문하기 전에 자주 묻는 질문과 주요 공지를 한곳에서 확인할 수 있고, 필요하면 AI 채팅으로 자연스럽게 물어볼 수 있습니다. 해결되지 않은 문의는 부서별 전화번호를 바로 확인해 연결할 수 있어, 홈페이지를 여러 번 탐색하지 않아도 필요한 정보를 얻습니다.

정보 탐색 경로를 아래 3단계로 좁힌 것이 핵심입니다.

```
① 먼저 보여주기   자주 묻는 질문 · 인기 공지 (홈)
        ↓ 못 찾으면
② 물어보기        AI 학사 상담 챗봇
        ↓ AI가 확신 못 하면
③ 사람에게        상담사 연결(핸드오프) / 부서 전화번호
```

## 4. 핵심 기능

| 기능 | 설명 |
| --- | --- |
| **AI 학사 상담 챗봇** | 주제 선택 없이 자유롭게 질문하면 학교 자료(FAQ·공지·체크리스트·연락처)를 근거로 답변한다 |
| **상담사 연결 (핸드오프)** | AI가 확신하지 못하는 질문은 **학번·학과·이름**을 받아 상담사 전용 채팅을 새로 열어 연결한다 |
| **실시간 채팅 및 대화 기록** | 로그인 없이(익명 인증) 상담사 답변을 실시간으로 받고, 지난 대화 기록도 이어본다 |
| **문의 통계 분류** | 학생 질문을 카테고리·주제별로 자동 분류해 관리자가 문의 추이를 파악한다 |
| **부서 전화번호 안내** | 학내 부서 연락처를 분류·검색해 바로 통화 연결한다 |
| **홈 화면** | 검색창이 곧 챗봇 진입구이며, 자주 묻는 질문과 인기 공지를 함께 제공한다 |

### 4.1 화면 구성 (학생 웹 `han-non-e`)

| 화면 | 경로 | 역할 |
| --- | --- | --- |
| 홈 | `/` | 히어로 검색바(→ 채팅 직행) · 카테고리 카드 · 인기 검색어 · FAQ · 인기 공지 |
| 채팅 | `/chat` | AI 상담, 상담사 핸드오프, 이전 대화 기록 패널 |
| 공지 | `/notices` | 원문 공지 목록 |
| 전화번호부 | `/directory` | 부서별 연락처 분류·검색 · `tel:` 연결 |
| 검색 | `/search` | 키워드 검색 결과 |

화면별 상세 UI 규칙은 [DESIGN.md](DESIGN.md) §7~§8을 참고하세요.

### 4.2 관리자 앱 (`han-non-e-admin`)

운영 통계 · 채팅 상담 응대 · 전화 문의 기록 · 콘텐츠(카테고리/FAQ/공지/체크리스트) 관리.
자세한 기능과 Firestore 컬렉션 구조는 [README.md](../README.md)에 정리돼 있습니다.

## 5. 사용자 피드백과 반영 결과

| # | 피드백 | 상태 | 반영 내용 |
| --- | --- | --- | --- |
| 1 | 메인 페이지 UI가 밍밍하고 통일이 필요함 | ✅ 반영 | UI 전면 개편 |
| 2 | 채팅이 핵심이니 채팅을 메인 화면으로 올리는 게 좋겠음 | ✅ 반영 | 채팅 메인 배치 |
| 3 | 담당자 채팅 문의 시 학과·학번을 아무거나 입력해도 접속됨 → 필터링 필요 | ✅ 반영 | 입력 검증 로직 추가 |
| 4 | 담당자가 공지를 수기 등록하는데, 원문 공지가 있다면 AI가 분류하게 하는 게 좋겠음 | ⏳ 계획 | §6 고도화 계획 |

### 5.1 UI 전면 개편 & 채팅 메인 배치 (피드백 1·2)

"메인이 밍밍하고 통일감이 없다"는 피드백을 반영해 화면 전반을 다시 설계했습니다.

- 색상·레이아웃·컴포넌트 톤을 하나로 통일하고 정보 위계를 정리.
- **우측 하단 위젯으로만 있던 채팅을 메인 화면 중심으로 끌어올려**, 사이트 전체가 채팅 중심으로 동작하도록 재설계.
  - 홈 검색바 제출이 검색 결과가 아니라 `/chat?q=...`로 **직행**하는 구조가 이 변경의 결과입니다.
  - 기존 플로팅 위젯 스타일은 현재 미사용 레거시로 남아 있습니다 → [DESIGN.md 부록](DESIGN.md#부록-미사용레거시-스타일).
- 디자인 언어(따뜻한 크림·앰버 팔레트, 24px 라운드, 넓게 퍼지는 옅은 그림자, **AI=앰버 / 상담사=블루**)는 [DESIGN.md](DESIGN.md)에 시스템으로 문서화.

### 5.2 담당자 채팅 접속 필터링 (피드백 3)

기존에는 학과·학번에 아무 값이나 넣어도 상담사 채팅에 접속됐습니다. 검증 로직을 넣어 유효하지 않은 입력은 차단합니다.

- 학번: 숫자 고정 자릿수(`inputMode="numeric"`), 학과: `datalist` 자동완성, 이름: 필수.
- 세 값이 모두 유효할 때만 제출 버튼 활성화, 필드별 오류/경고 문구 자리를 고정해 레이아웃이 흔들리지 않게 처리.
- 상세는 [DESIGN.md §8.3](DESIGN.md#83-상담사-연결-모달).

## 6. 남은 문제와 고도화 계획

### 6.1 남은 문제 — 공지 등록이 여전히 수작업

지금 관리자는 학교 공지를 한 건씩 손으로 옮깁니다. 제목·링크·카테고리를 매번 입력해 **공지 하나에 3분 이상** 걸립니다.

더 큰 문제는 **저장되는 게 제목과 링크뿐**이라는 점입니다.

```
공지 본문이 없음
   → AI가 공지 내용을 모름
   → "전과 신청 언제까지예요?"에 답하지 못함
   → 상담사 연결로 넘어옴
   → 관리자가 또 손으로 답변
```

관리자 업무가 늘어나는 구조 자체가 여기서 시작됩니다.

### 6.2 고도화 계획 — 공지 수집 자동화

학교 공지를 자동으로 수집하고, AI가 **카테고리·신청기간·요약**까지 구조화해 관리자 화면에 **'승인 대기'**로 띄웁니다. 관리자는 확인하고 승인만 누릅니다.

- **입력 시간: 3분 → 10초**
- **부수 효과**: 이때 만든 요약이 그대로 AI의 지식이 됨 → AI가 공지 내용으로 답하기 시작 → 상담 문의 자체가 감소
- 관리자의 일이 **"입력하고 답변하기"에서 "승인하기"로** 바뀜

> 구현 설계(서버 엔드포인트, 데이터 스키마, 단계별 로드맵, 비용, 리스크)는 [AI_PLAN.md](AI_PLAN.md)의 **P1. 공지 등록 자동화**에 정리돼 있습니다. 이 문서의 고도화 계획이 곧 AI_PLAN의 Phase 1입니다.

원문 정리본(PDF)을 옮기면서 조정한 부분입니다.
